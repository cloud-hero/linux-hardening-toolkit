EVIDENCE CHECKS
Every command below names evidence to read in the supplied pack or request from the authorized operator. It is not permission for the model to execute anything. The operator reviews any follow-up, uses their existing approved access and privileges on the Linux server, and returns a redacted receipt. The model continues analysing evidence on the separate workstation.

1. SSH ACCESS
Review supplied /usr/sbin/sshd -t and /usr/sbin/sshd -T output. Extract only PermitRootLogin, PubkeyAuthentication, PasswordAuthentication, KbdInteractiveAuthentication, AuthenticationMethods, UsePAM, AllowUsers/AllowGroups, forwarding controls, ListenAddress/Port, and LogLevel. Inspect Include order and relevant Match criteria without printing key material. For each approved admin/source combination require operator-supplied output of sshd -T -C user=ACTUAL_USER,host=ACTUAL_CLIENT_HOST,addr=ACTUAL_SOURCE_IP; supply laddr/lport if Match uses them. Require root's context too. Match Host is the connecting client's resolved hostname, not the server name.
Expected: no direct root login, individual identities, approved key/certificate or MFA authentication, no unintended password-only path, justified forwarding, and access limited to approved users/networks. Keyboard-interactive may intentionally support PAM MFA: assess the complete AuthenticationMethods policy before recommending disabling it. Existing session success is not proof of a fresh login. Fresh authorized key login, privilege escalation, and console recovery are MANUAL unless separately demonstrated without creating credentials. Do not brute-force or attempt passwords.

2. PATCH MANAGEMENT
Inspect package manager sources and signing policy with secrets redacted, package holds, installed versions, available candidate versions, periodic settings, timer enablement/last run, and last successful update evidence. On Ubuntu review supplied output from apt-mark showhold, apt-get -s upgrade, apt-get -s --with-new-pkgs upgrade, dpkg --audit, apt-config dump filtered to APT::Periodic and Unattended-Upgrade settings, and systemctl list-timers apt-daily.timer apt-daily-upgrade.timer. On Fedora and Amazon Linux 2023 review the RPM inventory, DNF/DNF5 cached update observations, update service states and allowlisted signing/automatic-update configuration. DNF exit 100 means cached updates exist, not a failed command. A missing tool or repository cache remains missing evidence. Amazon Linux 2023 is repository-version-locked; no updates inside its current pin does not prove it is on the latest release. Inspect metadata timestamps and repository coverage; do not refresh them. A simulation may understate exposure when metadata is stale. Check third-party repositories and applications outside APT separately. Approved deployment pipelines may replace automatic installs; require their success evidence and deadline policy. Automatic reboots and package-triggered service restarts are different controls.
For a requested CVE, consult the distribution vendor's advisory for this exact release, source/binary package, architecture and repository/entitlement. Compare full vendor package revisions with the vendor's version comparator. Include the advisory URL and collection date. Distinguish affected, fixed installed, fixed active, not affected, and unknown. If unavailable, say unknown. Never equate a lower upstream version with vulnerability: distributions backport fixes.

3. KERNEL LIFECYCLE
Require supplied observations for uname -r, installed kernel image/meta packages, current kernel package ownership, configured/default next-boot kernel, boot space, reboot markers, and support status for OS plus kernel track. On Ubuntu inspect dpkg-query for linux-image-* and /run/reboot-required{,.pkgs}; do not infer next boot from the newest filename. If the bootloader cannot be resolved, record MANUAL. List-only needrestart -r l may help identify stale processes when its installed behavior is verified; never authorize automatic restarts. Review supplied livepatch status only if installed; verify this kernel and the specific CVE are covered. Record whether a tested fallback kernel and console recovery exist. A new package on disk is not proof the running kernel is patched.

4. FIREWALL EXPOSURE
Require supplied ss -lntu output; the effective host rules using the active manager (ufw status verbose, nft list ruleset, or firewall-cmd read operations, as applicable); interfaces/address families; cloud firewall/security-group evidence if supplied; load balancer and container port mappings. Do not install or enable another firewall manager. Compare expected services with listeners and allowed ingress for BOTH IPv4 and IPv6, including UDP. 5. AUDIT LOGGING

A running auditd with zero relevant rules does not establish coverage. Do not create marker events in observational mode. Local retention, central delivery, tamper resistance, and human response are distinct checks. Avoid reading raw application/security events unless the user explicitly supplies or authorizes a narrow redacted sample.

6. CONFIGURATION DRIFT
Compare current settings, package inventory, file ownership/mode, service enablement, firewall rules, and kernel track with a trusted, versioned approved baseline. Inspect the provenance and approved scope before requesting any comparison. The companion baseline.py check compares names, types, ownership, modes, symlink targets and content for explicit paths. A sha256sum --check result alone covers only the listed file bytes and cannot establish complete inventory coverage. A local manifest can be rewritten by root; it is not independent attestation. Check for extra files as well as changed/missing files, particularly SSH drop-ins and service overrides. Do not run arbitrary configuration-management plugins or playbooks just because they have '--check'. Report drift with expected/observed values, owner, exception expiry, and proposed reconciliation. Do not silently refresh the baseline to bless drift.

Application probes must be authorized and have known side effects. Do not treat HTTP 200 from a health endpoint as a complete transaction test. Record missing tests as MANUAL. This assessment must not reboot a host or declare a maintenance window complete.

FIXED CONTROL CONTRACT
The embedded LH-1.2 catalogue is authoritative: emit exactly one result for each of its 28 IDs, in catalogue order. Do not invent, split, combine, omit or renumber controls. Evaluate every required criterion. Apply this precedence: (1) evidence-backed N/A only when the applicability condition is met and an approver is recorded; (2) FAIL when any criterion is proven unmet, retaining other collection gaps in the rationale; (3) ERROR when a required attempted observation failed and no failure was already established; (4) MANUAL when required evidence, policy or current proof is missing; (5) WARN only when all required evidence is present, no criterion fails, and a named policy warning threshold is reached, such as approaching a deadline; (6) PASS when every criterion is satisfied. Do not use WARN as a substitute for missing evidence. An approved exception does not change FAIL to PASS. The absence of production infrastructure or a tool is not itself N/A. Additional findings belong in an unscored appendix.

REPORT FORMAT
Write a local Markdown report with:
- Scope, identity, UTC timestamp, OS/kernel, privileges, baseline revision and explicit limitations.
- A row per check: ID, PASS/FAIL/WARN/MANUAL/ERROR/N/A, expected state, observed state, command/evidence reference, impact, and confidence. N/A requires a reason. WARN means an explicit policy warning threshold is met with complete required evidence; ERROR means collection failed; MANUAL means further evidence or policy is needed. Use the precedence above.
- Coverage: counts over the fixed 28 IDs, with evidenced checks (PASS+FAIL+WARN) divided by (28 minus justified N/A). If every check is N/A, coverage is undefined, not 100%. Also state complete passes and unresolved controls. This is evidence coverage, not a security score or risk measure. Compare runs only when catalogue version, applicability and scope match.
- Prioritized findings: immediate exposure, patch/support gaps, detection gaps, and operational improvements. Give owner, due date or policy deadline, dependencies, rollback, proposed fix marked 'NOT RUN', and exact post-change verification.
- Unscored CVE/incident appendix when intelligence is supplied or a CVE review is requested: advisory, affected release/package, installed vendor revision, fixed revision, running/loaded state, exploit prerequisites, and remaining uncertainty.
- A handoff checklist for approved remediation and repeat assessment after maintenance.
Finish with the three most important findings and the most consequential missing evidence. Do not apply any fixes.

Also produce report.json using the supplied report template. Include baseline_version, target, evidence_scope, assessed_at and exactly 28 checks. Each check has id, status, rationale, evidence (a list of source, observed_at, observation, method), and exception (null or the approved record). N/A also requires na_reason and na_approver. PASS/FAIL/WARN require evidence; MANUAL/ERROR require the missing observation or collection failure in rationale. An operator can run check-report.py with controls.json to reject missing/duplicate IDs and recompute counts. It validates structure, not truth.


FIXED LH-1.2 CONTROL CATALOGUE (28 CONTROLS)

SSH-01 | Effective authentication
PASS requires: Root login is disabled; every user/source Match context enforces the approved key/certificate or MFA chain; no unintended password-only route.
Required evidence: sshd -t; sshd -T -C for each approved context and root; approved authentication policy.
Applicability: Always applicable to a server offering SSH.

SSH-02 | Identity and key lifecycle
PASS requires: Every privileged identity/key/CA has an owner, justified privilege, revocation path and current access review.
Required evidence: Redacted identity inventory, sudo scope, key/CA lifecycle and offboarding evidence.
Applicability: Always applicable; non-SSH administration uses equivalent identity evidence.

SSH-03 | Fresh access verification
PASS requires: A new non-multiplexed session and required sudo action succeed after change; forbidden authentication is rejected in an authorized test.
Required evidence: Timestamped new-session receipt, effective forbidden-authentication policy and bounded negative test.
Applicability: Always applicable when SSH is the management path.

SSH-04 | Recovery and revocation
PASS requires: The approved console/break-glass route and an access-revocation exercise meet the organization recovery objective.
Required evidence: Dated recovery/revocation exercise, responsible owner, credential storage and retrieval record.
Applicability: Always applicable; do not perform a recovery drill during observational assessment.

PATCH-01 | Supported sources and coverage
PASS requires: OS release, kernel track and repositories are supported, signatures verified and every software channel has an update owner.
Required evidence: Release/support evidence, repository signing configuration, entitlement status, third-party/runtime inventory.
Applicability: Always applicable.

PATCH-02 | Fresh update inventory
PASS requires: All required indexes have a successful refresh within policy; all pending/held packages are identified using both ordinary and new-dependency simulations.
Required evidence: Refresh receipt for every source, metadata age, apt holds, simulations, dpkg audit.
Applicability: Always applicable; use vendor equivalents outside Ubuntu.

PATCH-03 | Patch execution evidence
PASS requires: The approved pipeline or unattended policy has successful runs, intended origins, monitored failures and controlled restart/reboot behavior.
Required evidence: Effective allowed origins and periodic settings, timer/job state, successful transaction and failure alert receipt.
Applicability: Always applicable; a managed pipeline is a valid alternative to unattended installs.

PATCH-04 | Remediation deadlines
PASS requires: Every applicable overdue fix has an approved, unexpired exception; no unowned exposed vulnerability remains.
Required evidence: CVE/package mapping, exposure, owner, due date, exception approver and compensating control.
Applicability: Always applicable; no open findings still requires the current inventory and policy.

KERN-01 | Kernel track and boot capacity
PASS requires: The approved supported flavour/meta-package is present; boot/root free space supports the reviewed transaction and recovery image.
Required evidence: Package/candidate records, vendor support track, bootloader type, disk capacity.
Applicability: Always applicable to hosts; a container points to an identified host owner, not an automatic N/A.

KERN-02 | Installed and active fix state
PASS requires: Running kernel, installed fixed revision and actual next-boot selection are reconciled; livepatch claims name specific coverage.
Required evidence: uname -r; package ownership/version; actual bootloader entries; vendor advisory; livepatch evidence if used.
Applicability: Always applicable to the assessed host. Livepatch itself can be unused without making the control N/A.

KERN-03 | Verified reboot activation
PASS requires: Required reboot is completed within policy and the intended kernel is active with working drivers, networking and workloads.
Required evidence: Changed boot ID, post-boot kernel, restart-needs check and workload acceptance record.
Applicability: For a maintenance assessment. For a baseline audit, use a recent approved exercise; absent evidence is MANUAL.

KERN-04 | Fallback boot recovery
PASS requires: A retained recovery option has been exercised and can restore service within the approved recovery objective.
Required evidence: Actual fallback/recovery exercise, console access, application recovery and vulnerability re-triage record.
Applicability: Always applicable; an image-replacement strategy can substitute for an older-kernel boot.

NET-01 | Approved exposure inventory
PASS requires: Every listener maps to an owned service with expected protocol, family, source and destination; unused services are removed or explicitly excepted.
Required evidence: Service-exposure inventory and ss listener comparison.
Applicability: Always applicable, including non-public hosts.

NET-02 | Effective host and platform policy
PASS requires: Host rules, cloud/network policies and container forwarding permit only the approved paths across IPv4 and every deployed IPv6 path.
Required evidence: Effective rules, management-source restrictions, cloud/load-balancer evidence and container mappings.
Applicability: Always applicable. Undeployed layers need an evidence-backed reason, not guessed absence.

NET-03 | Allowed and denied path proof
PASS requires: Authorized probes confirm expected access and rejection from named management and untrusted vantage points, including deployed UDP services.
Required evidence: Source/destination/protocol/family matrix with live-listener positive and negative results.
Applicability: Always applicable; no external vantage point means MANUAL for external exposure.

NET-04 | Firewall recovery
PASS requires: The prior approved rules can be restored through a tested independent access path and required services recover.
Required evidence: Rollback exercise, saved exact policy and post-restore access/health evidence.
Applicability: Always applicable; observational mode consumes existing evidence only.

AUD-01 | Useful event coverage
PASS requires: Persistent audit rules and authentication/privilege logs cover the approved event inventory and controlled events are retrievable.
Required evidence: Loaded and persistent rules, event inventory, redacted audit/authentication event examples.
Applicability: Always applicable; alternative audit mechanisms require documented equivalent evidence.

AUD-02 | Retention and pressure behavior
PASS requires: Journal and audit-log limits separately match policy; rotation, free-space/queue alerts and failure actions are verified under safe test conditions.
Required evidence: Effective journald and auditd settings, retention calculation, rotation result, disk/queue alert exercise.
Applicability: Always applicable; a configured limit alone is not a retention guarantee.

AUD-03 | Authenticated central delivery

Required evidence: TLS peer verification, unique marker receipt, audit-event receipt, negative TLS result, outage/recovery and queue evidence.

Required evidence: Clock status, receiver retention/access policy, alert receipt/acknowledgement and response owner.

DRIFT-01 | Trusted desired state

DRIFT-03 | Runtime and package drift

VERIFY-04 | Controlled rollout decision
PASS requires: Canary acceptance, rollback rehearsal, staged rollout and final owner sign-off are recorded; failed gates stop advancement.
Required evidence: Release decision record with canary count, gates, rollback result and sign-off.
Applicability: Always applicable; assessment alone never authorizes a production rollout.
